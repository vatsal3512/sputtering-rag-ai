What This Project Does

This system ingests 5,000+ academic research papers on thin-film sputtering deposition, extracts structured experimental parameters from them using an LLM, embeds everything into a scientific vector database, and exposes all of it through a two-tab interactive dashboard.

The output in one sentence A researcher types "ZnO" and instantly gets the mean deposition power, median working pressure, most common substrate, and distribution charts — aggregated from hundreds of papers that would otherwise take days to read manually.

Concrete Example

Input (Tab 1): User types ZnO

Output (Tab 1):

  • AI groups aliases: ZnO, zinc oxide, Zn0, ZnO:Al, ZnO:Ga
  • Found: 312 papers in the ZnO family
  • Mean power: 127 W  |  Median: 100 W  |  Range: 5–500 W
  • Mean pressure: 0.53 Pa  |  Most common substrate: Glass
  • Interactive charts: power histogram, temperature distribution, substrate bar chart

Input (Tab 2): "What are the exact parameters for YBCO deposition in paper 10.1016/xyz?"

Output (Tab 2): The AI retrieves the specific paper from the vector database and answers with exact values, citing the Paper_ID. It cannot hallucinate — it can only report what's in the database.

The Problem It Solves

Domain Background

Thin-film sputtering is a physical vapour deposition technique where ions from a plasma knock atoms off a solid target material. Those atoms travel through vacuum and deposit as a nanometer-scale film on a substrate. It's used to make solar cells, sensors, hard coatings, touchscreen electrodes (ITO), and superconducting films.

To deposit a specific material — say, Zinc Oxide (ZnO) — a researcher must choose: what RF power to apply, at what chamber pressure, using what gas mixture (Ar/O₂ ratio), on what substrate, at what temperature. Get any of these wrong and the film has the wrong properties.

The Old Manual Process

  1. Search Google Scholar / Web of Science for "ZnO sputtering"
  2. Download 50–200 papers
  3. Read the Experimental section of each paper
  4. Manually note parameters — but they're written differently in every paper:
Paper A: "RF power of 150 W at 5 mTorr Ar/O2 (4:1) gas ratio"
Paper B: "2 W/cm² power density, working pressure 0.67 Pa, pure Ar atmosphere"
Paper C: "100-200 W, argon flow 40 sccm, oxygen 10 sccm, 3×10⁻³ Torr"

All three describe similar conditions but in incompatible notation. Comparing them requires manual unit conversion.

What This System Provides

The same researcher opens the dashboard, types "ZnO", and gets the answer in seconds — aggregated from 312 papers, with all units normalised to Pa/W/nm/°C.

Time saved Manual literature survey: 3–7 days. This system: <10 seconds query time after the one-time pipeline setup.

Tech Stack — Every Choice Justified

4.1 — GROBID: PDF Parser

✓ Chosen

GROBID is a machine-learning library that converts academic PDFs into structured TEI XML, correctly identifying titles, abstracts, section headings, body paragraphs, tables, and references. It is used in production by Semantic Scholar and CrossRef to parse millions of papers.

Alternative Why it doesn't work
PyPDF2 / pdfplumber Extracts raw text with no structure. Cannot identify which text is a section heading vs. a paragraph vs. a table. Two-column layouts become garbled.
Adobe PDF Extract API Paid service, requires internet per request, returns flat text without scholarly structure awareness.
LLM-based PDF parsing PDF pages as images sent to a vision LLM is expensive (~$0.01–0.10 per page), slow, and has hallucination risk for layout detection.
GROBID ✓ Free, open source, trained specifically on scientific papers, preserves full document structure, correctly identifies the Experimental/Methods section — exactly where parameters live.

4.2 — Gemini 2.5 Flash: LLM for NER Extraction

✓ Chosen

Used as a structured extractor, not a chatbot. Given paper text, it outputs a JSON object with 10 fields. This is a 2024-era pattern: LLM-as-parser.

Alternative Why it doesn't work
spaCy / NLTK NER Traditional NER models are trained on fixed entity types (Person, Location, Organisation). Cannot extract domain-specific numeric values with units from unstructured prose.
Fine-tuned BERT Would need thousands of labelled examples (paper text → JSON) to fine-tune. Not available for sputtering domain. Training cost is high.
GPT-4 Works equally well or better but costs ~10× more per token. At 5,000 papers this matters.
Gemini 2.5 Flash ✓ Free tier with generous daily quotas, fast response, reliably follows complex JSON schema instructions, supports multi-key rotation to handle rate limits across 5,000 papers.
Critical: LLM is NOT used for statistics If you ask an LLM "what is the mean power for ZnO?", it will confidently give you a wrong number. The LLM is used only where it excels: reading prose and extracting structure. Statistics are computed by pandas from the actual database.

4.3 — SPECTER (allenai-specter): Scientific Embedding Model

✓ Chosen — Most important choice in the stack

Converts each paper record into a 768-dimensional vector that captures semantic meaning. Similar records cluster together in vector space, enabling "find papers about high-power ZnO deposition" as a nearest-neighbour search.

Alternative Why it's wrong for this project
all-MiniLM-L6-v2 (ChromaDB default) Trained on general English (Reddit, Wikipedia, news). Does not understand "HiPIMS", "MTorr", "sputtering yield", or "reactive deposition" as scientific concepts. A query for "high power deposition" might retrieve papers about electrical grid power.
text-embedding-004 (Google Cloud) Cloud API — requires internet and paid API call for every single user query. Adds latency and cost. App cannot work offline. At 5,293 vectors × N queries per day, this becomes expensive.
SciBERT (allenai/scibert_scivocab_uncased) Trained on 1.14M scientific papers via masked language modelling (MLM). MLM is optimised for token-level tasks (classification, NER) — not for generating document-level similarity vectors. SciBERT embeddings are not well-calibrated for semantic similarity ranking.
OpenAI text-embedding-3-small Paid API, cloud dependency, general-purpose (same issue as MiniLM for scientific jargon).
SPECTER ✓ Trained by AllenAI specifically for scientific document similarity. Training task: "paper A and paper B (which A cites) should embed close together." This directly matches the use case: "query about sputtering parameters should retrieve the most similar paper records." Runs 100% locally. No API key. No internet needed after first download.

4.4 — ChromaDB: Vector Database

✓ Chosen
Alternative Why it doesn't fit
Pinecone / Weaviate Cloud-hosted. Requires account, API key, internet. Not suitable for a local research tool in a lab environment.
FAISS (Facebook) Library, not a database. No persistence layer — must manually save/load index. No metadata filtering. Complex API.
Qdrant Good alternative, but requires Docker to run properly. Overkill for a single-machine research tool with <10K vectors.
ChromaDB ✓ Zero-configuration file-based persistence (one chroma.sqlite3 file). Native Python API. Supports metadata filtering. Open source. At 5,293 vectors, query latency is <100ms on CPU. Scales to ~1M vectors before needing a dedicated server.

4.5 — LangChain + LangGraph: AI Application Framework

✓ Chosen (for app.py only — not for pipeline scripts)

LangChain provides:

  • ChatGoogleGenerativeAI — standard interface over Gemini (swappable with any other LLM)
  • ChatPromptTemplate — structured prompts with typed variables; system role separated from human role
  • PydanticOutputParser — enforces that LLM output parses into a typed Python object

LangGraph provides the routing agent:

User Query → Router Node → "retrieval"   → Retrieval Node → answer
                         → "statistical" → Redirect Node  → "use Tab 1"

Why this matters: The original code used a prompt instruction ("if user asks for stats, say X"). LLMs can ignore prompt instructions. With LangGraph, the retrieval node is literally unreachable from a statistical query — routing is enforced in Python code, not in text.

Why pipeline scripts still use raw Gemini SDK LangChain adds value when you need composability (chain operators), structured parsers, or standard interfaces. The pipeline scripts make direct API calls with f-string prompts — they don't need composability, and the few-shot f-string prompt is clearer and easier to maintain for that context.

4.6 — Pydantic: Schema Validation

✓ Chosen

Every LLM JSON response in the extraction pipeline is validated against a strict schema before being written to disk.

class ExtractionResult(BaseModel):
    Material:          str
    Substrate:         str
    Deposition_Method: str
    Power:             str
    # ... 10 fields, all required, all str

try:
    validated = ExtractionResult.model_validate_json(raw_llm_response)
    json.dump(validated.model_dump(), output_file)   # ← only clean data written
except ValidationError as e:
    logging.warning(f"Skipped: {e}")                 # ← bad response logged, skipped

Without this: A null field or missing key from Gemini gets written to disk. The next stage crashes silently or produces incorrect statistics. The bug is invisible.

With this: The database is guaranteed clean. All failures are logged to extraction_errors.log with the raw response for inspection.

4.7 — Streamlit: Dashboard Framework

✓ Chosen

Users are domain scientists, not web developers. Priorities: correct data analysis, fast iteration, interactive charts. Streamlit converts Python data science code directly into a web UI:

# This one line renders a full interactive histogram with a box plot:
st.plotly_chart(px.histogram(df, x="Power_W", nbins=50, marginal="box"))

The equivalent in React+D3 would be 3 files and 100+ lines. For a research tool, this trade-off is correct.

The Pipeline — Stage by Stage

STAGE 1 full_grobid_pipeline.py — PDF → Structured JSON
Input
*.grobid.tei.xml (TEI XML files)
Output
structured_data.json per paper

What GROBID does first (external — cloud server): Takes a raw PDF, uses ML models to identify document structure, returns TEI XML with labelled sections: <title>, <abstract>, <body><div> etc.

What this script does:

  1. Parses TEI XML using BeautifulSoup's xml parser (requires lxml)
  2. Extracts title, abstract, and all body <div> sections
  3. For each paragraph, runs a 30-term keyword filter (sputter, pressure, argon, magnetron, HiPIMS...)
  4. Keeps only paragraphs containing sputtering-relevant content
  5. Saves clean JSON per paper
Why keyword filter here? Each paper has ~20–50 paragraphs. Sending all to the LLM in Stage 2 wastes tokens (cost + latency) and dilutes the relevant content (lower accuracy). The filter keeps only methodology paragraphs, reducing token count by ~70% with negligible information loss.

Output format:

{
  "paper_id": "paper_slug",
  "title": "ZnO thin films deposited by...",
  "abstract": "We report on the deposition of...",
  "sections": [
    {
      "heading": "Experimental",
      "text": "Films were deposited by RF magnetron sputtering at 150 W..."
    }
  ]
}
STAGE 2 master_data_extraction.py — Gemini NER
Input
structured_data.json per paper
Output
paper_extracted.json per paper

The 3-shot few-shot prompt: Three real-world examples precede each paper's actual text. This calibrates the LLM for edge cases:

TEXT: "ZnO films on glass by RF sputtering at 150 W, Ar/O2 (4:1), 5 mTorr, 300°C"
OUTPUT: {"Material":"ZnO","Substrate":"Glass","Power":"150 W","Working_Pressure":"5 mTorr",...}

TEXT: "TiN coatings by DC reactive sputtering from Ti target, N2/Ar, 2 Pa, 40 W/cm²"
OUTPUT: {"Material":"TiN","Deposition_Method":"DC Reactive Sputtering","Power":"40 W/cm²",...}

TEXT: "ITO on PET by HiPIMS, 3 mTorr, 2 kW peak, room temperature, 120 nm"
OUTPUT: {"Material":"ITO","Substrate":"PET","Deposition_Method":"HiPIMS","Film_Thickness":"120 nm",...}

Now extract from: {actual paper text}

Why 3 examples? Edge cases that fail zero-shot: "2 kW peak" (is it kW or W?), "room temperature" (is it RT or 25°C?), "100-200 W" (take lower bound? midpoint?). The examples enforce a consistent style.

API key rotation + rate limiting: 4.5s sleep between calls. On quota exhaustion after 3 retries → rotate to next key from .env. Pipeline saves progress after each paper — can resume after interruption.

Pydantic validation: All 10 fields must be strings. Validation errors logged to extraction_errors.log, paper skipped cleanly.

STAGE 3 post_processing_eda.py — Unit Normalisation
Input
All *_extracted.json files
Output
sputtering_database_clean.csv
Parser Function Handles Outputs
parse_pressure() MTorr, Torr, mbar, bar, Pa, scientific notation (5×10⁻³) Pa (float)
parse_temperature() K, °C, "RT", "room temperature", "room temp" °C (float)
parse_thickness() Å, nm, μm, mm nm (float)
parse_power() W, kW, mW, W/cm² W (float)
clean_gas_mixture() "Argon + oxygen", "Ar 80% O2 20%", "pure Ar" Ar/O2/N2/H2 tags

Scientific notation example: "5×10⁻³ Torr" → 5 × 10⁻³ × 133.322 Pa = 0.667 Pa

Outlier threshold: Films >2,000 nm excluded from EDA plots. This is a documented constant (thickness_outlier_threshold_nm in config.json), not a magic number.

STAGE 4 post_processing2.py — Sputtering Filter
Input
sputtering_database_clean.csv
Output
sputtering_database_clean_final.csv

Filters the Method column for keywords: sputter, magnetron, hipims, ibs, ion beam, rfms, dcms, pulsed dc. Removes rows where the LLM extracted a non-sputtering paper (CVD, ALD, PLD, e-beam) that slipped through Stage 2's prompt.

STAGE 5 build_vector_db.py — SPECTER Embedding → ChromaDB
Input
sputtering_database_clean_final.csv
Output
vector_database/chroma.sqlite3

Document format (what gets embedded):

Material: ZnO | Substrate: Glass | Deposition Method: RF Magnetron Sputtering |
Gas Mixture: Ar/O2 | Target Power: 150.0 W | Working Pressure: 0.667 Pa |
Base Pressure: Not specified | Substrate Temperature: 300.0 °C | Film Thickness: 500.0 nm

Why labelled key-value format over a sentence?
The original format was "To deposit ZnO on a Glass substrate using RF Magnetron Sputtering..." — a reconstructed sentence where "ZnO" is just another word. SPECTER cannot distinguish material from substrate from value. The labelled format preserves all semantic distinctions and enables accurate multi-condition queries ("low pressure ZnO on flexible substrate").

Deduplication: drop_duplicates(subset=['Paper_ID']) before ingestion.

upsert() vs add(): add() crashes with DuplicateIDError if run twice. upsert() updates safely — script is idempotent.

The Application — Two-Tab Design

The Macro / Micro Split — The Most Important Design Decision

Core principle Macro (Tab 1) = pandas math. LLM used only for language tasks (alias grouping).
Micro (Tab 2) = LLM with retrieved context. Never used for arithmetic.

LLMs are excellent at language understanding. They are unreliable for arithmetic over large datasets. If you ask a chatbot "what is the mean power for ZnO?", it has two bad options:

  • Try to compute from memory → hallucination (wrong number, stated confidently)
  • Refuse → unhelpful

The Macro tab computes statistics using pandas on 5,293 actual rows. This is mathematically exact. The LLM's only role in Tab 1 is to group ["ZnO", "zinc oxide", "Zn0", "ZnO:Al"] into one family — a language task it handles perfectly.

Tab 1: Statistical Overview (Macro) — Full Flow

  1. User types a material name (e.g. ZnO)
  2. ChromaDB semantic search finds the 50 most relevant records using SPECTER
  3. All unique Material values from those 50 records are collected as candidates
  4. PydanticOutputParser calls Gemini: "which of these belong to the ZnO family?"
  5. Gemini returns a typed MaterialAliases(aliases=["ZnO", "zinc oxide", ...]) object
  6. The CSV is filtered to only rows matching those aliases
  7. pandas computes: mean, median, mode, min, max for Power, Temperature, Pressure
  8. Plotly renders 4 charts: substrate bar chart, power histogram, temperature histogram, pressure histogram

Tab 2: AI Chatbot (Micro) — Full Flow

  1. User asks: "What power was used for YBCO on MgO substrate?"
  2. LangGraph Router Node: Gemini classifies the query as "retrieval" or "statistical"
  3. If "retrieval": ChromaDB returns top-10 semantically similar records using SPECTER
  4. Gemini reads those 10 records + last 3 conversation turns → generates a grounded answer
  5. Sources listed below answer (Paper_IDs cited)
  6. If "statistical": Redirect message sent, no database access

Chat Memory

The last 3 conversation exchanges are injected into every prompt. Without this, follow-up questions fail:

User: What parameters were used for ZnO?
AI:   [lists parameters from 3 papers]

User: What about the substrate?   ← "substrate" refers to ZnO context
AI:   [without memory: "which material are you referring to?"]
      [with memory: correctly understands this is still about ZnO]

LangGraph Routing — Graph vs. Prompt

# Old: fragile prompt instruction (LLM can ignore it)
"RULE 4: If user asks for statistics, reply with 'I am the Micro bot...'"

# New: graph edge (enforced in Python code)
graph.add_conditional_edges("router", _route_decision, {
    "retrieval":   "retrieval",    # only reachable if router returns "retrieval"
    "statistical": "statistical",  # redirect node — zero database access
})

Key Architectural Decisions

Why Not One Big Chatbot?

The naive approach: one chatbot with access to the CSV, the vector DB, and let it handle everything. Problems:

  • LLMs cannot reliably compute mean/median/mode over thousands of rows
  • No separation between "hallucinated knowledge" and "database knowledge"
  • No grounding — which paper did this number come from?

The Macro/Micro split enforces an iron boundary: statistics come from pandas (exact), specific facts come from retrieved database entries (cited).

Why Store Extracted Fields, Not Full Paper Text?

Common RAG embeds full paper chunks and retrieves them. For this domain, the goal is not to reproduce the paper — it's to get specific numeric values. If full text is embedded and retrieved, the LLM must still parse numbers out of prose, reintroducing the NER problem. By running NER first (Stage 2) and storing structured fields, every query returns clean Power: 150 W, not prose.

Why config.json + config_loader.py?

Original: 6 scripts with hardcoded D:\UGP_METHOD2\... paths. Impossible to run on any other machine.

Solution: config.json defines all paths as relative paths (./data/grobid_xml). config_loader.py resolves them to absolute paths at runtime. Result: project works on any OS, any directory, for any user.

Why .env for API Keys?

Hardcoded API keys in source files get committed to Git and exposed publicly. .env files are gitignored. python-dotenv loads them at runtime. The .env.example template shows users exactly what to fill in without exposing real keys.

Why run_pipeline.py?

6 disconnected scripts run in a specific order with dependencies between them. Without an orchestrator, a new user must figure out the order, manually check which stages are done, and handle errors between scripts. run_pipeline.py chains all stages, implements skip logic (don't redo completed stages), and provides --stage / --from / --force flags for surgical re-runs.

How to Run

First-Time Setup (Dashboard only — no re-extraction needed)

# 1. Install all dependencies
pip install -r requirements.txt
# Note: SPECTER model (~400 MB) downloads on first use of build_vector_db.py

# 2. API keys (needed only for the app at runtime, not for building the vector DB)
copy .env.example .env
# Edit .env: add GEMINI_API_KEY_1=your_key_here

# 3. Rebuild vector DB with SPECTER (delete old ChromaDB first)
rmdir /s /q vector_database    # Windows
python build_vector_db.py
# Expected: "[OK] 5293 unique papers ready | Batch 1-100 / 5293 done | [DONE]"

# 4. Launch dashboard
python -m streamlit run app.py
# Open http://localhost:8501 — enter Gemini API key in sidebar

Running the Full Extraction Pipeline (for new papers)

python run_pipeline.py --list       # See all stages + done/pending status
python run_pipeline.py --stage 2    # Run only Gemini NER
python run_pipeline.py --stage 5    # Rebuild vector DB only
python run_pipeline.py --from 3     # Run stages 3 through 6
python run_pipeline.py              # Full pipeline (all 6 stages)

Minimum Requirements

  • Python 3.10+
  • ~2 GB disk space (SPECTER model cache + vector DB)
  • Gemini API key (free at aistudio.google.com) — only for app queries
  • Internet on first run only (to download SPECTER from HuggingFace)

Glossary

Sputtering
A physical vapour deposition technique where energetic ions knock atoms off a target material, which then deposit onto a substrate as a thin film.
RF Magnetron Sputtering
Uses radio-frequency (typically 13.56 MHz) power + magnetic field to sustain a plasma and improve deposition efficiency, especially for insulating targets.
HiPIMS
High Power Impulse Magnetron Sputtering — uses very high peak power in short pulses (low duty cycle). Produces denser, smoother films.
Working Pressure
Gas pressure inside the chamber during deposition. Typically 0.1–10 Pa. Affects mean free path of sputtered atoms and film morphology.
Base Pressure
Residual vacuum pressure before introducing process gas. Typically 10⁻⁴ to 10⁻⁶ Pa. Lower = fewer contaminants in the film.
TEI XML
Text Encoding Initiative XML — a scholarly standard for representing structured text with semantic markup. GROBID outputs this format.
NER
Named Entity Recognition — extracting structured information (entities) from unstructured text. Here: extracting "150 W" as the Power field from a paragraph.
RAG
Retrieval-Augmented Generation — LLM answers are grounded in retrieved documents rather than trained knowledge, preventing hallucination.
Vector Embedding
A high-dimensional numerical representation of text that captures semantic meaning. Similar texts produce similar vectors (close in vector space).
SPECTER
Scientific Paper Embeddings using Citation-informed TransformERs. An AllenAI model trained on 146M paper citation pairs for scientific document similarity.
Few-shot Prompting
Including 2–5 input/output examples in an LLM prompt before the actual input. Calibrates the LLM's output format and style for edge cases.
LangGraph
A framework for building stateful multi-step LLM workflows as directed graphs. Each node is a processing step; edges define routing logic.
